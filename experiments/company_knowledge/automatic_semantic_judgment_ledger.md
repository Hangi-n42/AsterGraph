### 상태를 읽는 방법

- **구성 미채택:** 특정 모델·입력·설정의 결과가 채택 기준에 미달했다. 방법 계열 전체의 불가능을 뜻하지 않는다.
- **부분 효과:** 정확한 변화가 관찰됐지만 다른 필수 결과나 별도 확인을 충족하지 못했다.
- **실행 전 중단:** 필요한 입력·자동 대응을 확보하지 못했다. 의미 정확도 0%로 쓰지 않는다.
- **후속 미실행:** 앞 단계가 필요한 정보/품질을 확보하지 못해 뒤 단계를 호출하지 않았다. 뒤 모델이 실패한 것과 다르다.
- **준비/제안:** 실행 결과가 확인되지 않았다. 기존 보고서의 준비 문단을 최종 상태로 오독하지 않는다.

### 완료를 분리하는 여섯 단계

`실행·주소 계약 → 의미 판정 → 오류 위치·이유 → 실제 편집·저장 → 정상 의미·같은 요구 재확인 → 그래프·검색·답변 활용`

앞 단계 통과는 뒤 단계 통과가 아니다. 라벨이 맞아도 이유가 틀릴 수 있으며, 설명이 맞아도 최종 라벨이 틀릴 수 있다. 코드가 기록을 보존하는 것과 모델이 의미를 정확히 판단하는 것도 다르다.

제품 완료 기준은 **“정상 의미를 유지하며 실제로 수정했고, 같은 요구를 다시 확인했으며, 필요한 후속 단계까지 이어졌다”**다. 연구 비교를 종료하거나 연구 이슈를 닫은 사실로 이 기준을 충족했다고 쓰지 않는다. 과거 보고서의 이슈 OPEN/CLOSED는 당시 상태이며 이 문서는 GitHub 최신 상태를 조회한 이슈 관리표가 아니다.

## 8. 다음 의사 결정과 갱신 방법

### 재시도를 정당화하는 변화

같은 방법을 다시 시도하려면 다음 중 실제로 달라지는 것을 기록한다.

1. **새 실패 원인 수정:** 종료 토큰·주소·문서 경계 같은 구체 결함을 고쳤고, 이전 실패와 구분해 검증한다.
2. **판단 메커니즘 변경:** 기존 실패 방식과 계산·입력·행동이 무엇이 다른지 설명한다. 새 필드명이나 논문 이름만 바뀐 것은 아니다.
3. **미확인 적용 범위 확인:** 부분 성공이 새로운 원문/정상 대조에서도 유지되는지 본다. 이를 개발 조정과 구분한다.

같은 실패에서 프롬프트·모델·입력을 여러 개 동시에 바꾸면 구성 전체의 결과만 주장할 수 있다. 유리한 라벨 배치·상대·seed·점수 부호·임계값을 사후 선택하지 않는다. 모든 방법을 무조건 다시 실행하는 비교 행렬도 만들지 않는다.

### 다음 기록을 추가할 때

- R 번호는 유지하고 새 완료 실험은 뒤에 추가한다. N 항목은 결과가 생기면 새 R 항목으로 연결하되 준비 시점 기록은 지우지 않는다.
- 어떤 이전 결과를 재사용했는지와 새 호출을 구분한다. 정답/질문이 바뀐 경우 원래 기준·수정 사유·영향 범위를 남긴다.
- 실행 전에 기준을 고정하고, 독립 확인 자료가 개발에 노출되면 그 시점을 자료 표에 반영한다.
- 연구 원리는 원 논문, 실제 적용은 코드/프롬프트, 성과는 원문·원시 응답에 각각 연결한다. 원형을 변형했다면 명시한다.
