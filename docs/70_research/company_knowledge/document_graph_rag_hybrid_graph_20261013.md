2026-10-13. **제품 연결·소규모 5질문 실제 검색·공통 독자 전달 방식 8QA 확인 완료. 전체 26문항·A 보조 비교는 미완료.**
기반은 `545e3ad88aded60528c6f79e18d0885547eeaa10`이며, 별도
`hybrid-graph-retrieval` checkout에서 구현했다. 기존 동결 자료·원본 DB·과거 응답은 보존했다. 전체 D01 구축은 실제 프로세스 종료로 중단됐으며 별도 복구 경계를 준비한다.

## 비교 목적과 변경

다음 비교의 C는 `hybrid_graph`를 명시하는 **C_v2**로 정의한다. 목적은 같은 원문에서 기존 Hybrid 검색에 현재 개념 그래프 검색 경로를 추가했을 때 필요한 근거·답변·비용이 어떻게 달라지는지 확인하는 것이다. 과거 C의 6문항 결과를 새 C의 결과로 재표기하지 않는다.

| 구분 | 검색 경로 | 제품 요청 |
|---|---|---|
| B | BM25 + 문서 임베딩 → RRF | `retrieval="hybrid"` |
| C_v1, 과거 기록 | 관계 선택 + 문서 임베딩을 이용한 그래프 PPR | `retrieval="hipporag2", graph_variant="full"` |
| C_v2, 다음 비교 | B의 Hybrid 순위 + 기존 그래프 PPR 순위 → RRF | `retrieval="hybrid_graph", graph_variant="full"` |

새 C가 무조건 더 정확하다는 가정은 없다. 이는 비교 목적을 맞추는 변경이다. 그래프 관계 선택 모델·전파·순위 결합 전체의 추가 효과를 측정하며, 연결 구조 하나의 순수 효과로 해석하지 않는다.

## 실제 동작

1. 동일한 전체 원문 풀과 제목·표·참조 문맥으로 BM25와 문서 임베딩 순위를 만든다. 추출된 관계가 없는 원문도 포함한다.
2. B와 같은 `RRFFusionStage`, `k=60`을 사용해 Hybrid 순위를 만든다.
3. 기존 C의 관계 후보 상위 30개 선택, 노드 seed 상위 10개, PPR 설정을 그대로 사용한다.
4. Hybrid와 그래프 순위를 동등한 두 순위 입력으로 RRF 결합한다. 그 뒤 기존 공통 문맥 선택과 동일한 답변 경로를 사용한다.
5. 선택된 graph seed가 없으면 B의 순위와 점수를 그대로 반환하고 `fallback="hybrid_passages"`, `graph_used=false`를 기록한다. 관계 선택 호출 실패는 fallback으로 숨기지 않고 기존 검색 실패로 처리한다.

수식은 `H(d)=1/(60+r_BM25(d))+1/(60+r_dense(d))`,
`C_v2(d)=1/(60+r_H(d))+1/(60+r_graph(d))`이다. 없는 순위의 기여는 0이다.
그래프 순위 자체에도 문서 임베딩이 들어가므로 두 입력은 독립 신호가 아니다. 별도 dense 순위를 세 번째 입력으로 더하지 않는다. 이 결합·상수의 최적성은 미확인이다.

저장 trace는 BM25·dense·Hybrid·graph·최종 순위, 선택 관계, seed, fallback을 구분한다. seed가 있다는 사실은 전파 실행을 의미하며, 유용한 순위 변화나 올바른 근거 확보를 보장하지 않는다.

## 제품 진입점과 비교 조건

기존 `POST /api/v1/knowledge/business/search`에 다음 요청을 사용한다. `source_run_id`와 질문은 다음 비교에서 고정한 실제 값으로 채운다.

```json
{
  "source_run_id": "<고정한 원문 추출 실행 ID>",
  "question": "<변경하지 않은 질문>",
  "retrieval": "hybrid_graph",
  "graph_variant": "full",
  "limit": 12,
  "source_context_tokens": 16384
}
```

B는 같은 요청에서 `retrieval`만 `hybrid`로 바꾼다. 서비스 직접 호출 시 B는 `context_mode="document"`, C_v2는 `context_mode="graph"`를 사용한다. 승인 snapshot 경로·UI 기본값은 이번 원문 검색 비교와 분리해 기존 값을 유지한다. 기존 동결 실행기를 그대로 돌리면 과거 `hipporag2`가 실행되므로, 다음 실행 manifest에서 **C_v2와 `hybrid_graph`를 명시**해야 한다. 과거 순위를 강제로 재사용하는 P2/P3/P4 runner는 새 검색 검증에 사용하지 않는다.

원문·자동 그래프 snapshot·질문·임베딩·답변 모델·공통 문맥 처리·최종 입력 한도를 동일하게 고정한다. 그래프나 질문을 정답에 맞춰 보완하거나 필수 정답 근거를 강제 삽입하지 않는다. 과거 C를 추가로 재실행하는 것은 항상 필수가 아니며, 동일 조건의 저장 응답만 재사용한다.

## 확인한 범위와 다음 검증

관련 32개 코드 검사에서 B의 RRF 산술 유지, C_v2의 두 단계 결합, 기존 C 순위 재사용, seed 없는 경우 B와 정확 동일, 관계 선택 실패의 명시 처리, 미추출 원문 보존, 공통 입력 예산·원본 DB 보존·서비스 답변 연결을 확인했다. 임베딩과 모델 응답은 모의 입력이므로 실제 품질 성과가 아니다.

기존 API 검사 1개도 통과했다. 확장한 변경 대응 검사 `test_knowledge_business_change_snapshot.py`의 12개 조합은 변경 전 HEAD 모듈과 변경 후 모두 `business_use.py`의 `reviewed_answer_connections()`에서 `KeyError: requirements`로 실패했다. 테스트의 원 실행 자료에 해당 키가 없으며 이번 변경 범위 밖이다. 전체 제품 검사가 통과했다고 보고하지 않는다.

소규모 단계에서 기존 누락 질문과 정상 대조의 근거 도달·답변을 확인했다. 다음 실행은 중단된 전체 원문 구축의 미완료 범위를 끝낸 후 고정한 26문항과 A 보조 비교로 확장한다. 일부 질문 전부 정답을 전체 실행의 선행조건으로 만들지 않는다. 개선·악화·동일·미확정, 그래프 전파/fallback, 구축 비용/질의 비용을 따로 집계한다.

BM25가 추가됐다는 이유로 기존 예외 적용·조건 판단 오류까지 해결됐다고 보고하지 않는다. 현재 사용자 결정이 필요한 사항 없음.

## 현재 관측과 공통 독자 전달 방식

소규모 5질문 원래 B/C_v2 실행은 B 3충족·2부분, C_v2 2충족·3부분이었다. 두 방식 모두 필수 근거 도달 4/5였고, C_v2가 항상 우수하다는 결과는 없었다. 이 원래 성적을 후속 reader 결과로 덮어쓰지 않는다. SUP03은 전체26 밖의 개발자 대조다.

같은 선택 원문을 확인된 DOM 가지 안에 직접 배치하는 공통 전달 방식을 4질문·8신규 QA에서 비교했다. 조율자의 고정 참조 대조는 개선3·유지5·관찰회귀0이다. SUP02 C의 거짓 공백이 제거됐고, ACT501108 B/C의 7년 미만 안내가 복원되면서 법적 창업 여부 미확정은 유지됐다. SUP01 B/C의 자금별 임차보증금 제외와 SUP03 B/C의 연2% 고정금리도 유지됐다. 이전 정상 ACT-B와의 대응은 별도 유지 근거이며 독립 5번째 질문이 아니다.

공통 원문 QA는 제품 버전 저장소의 해시가 일치하는 HTML과 해당 parse 계보를 읽는다. 여러 버전은 별도 문서 구조로 유지하고, 확인되지 않은 주소는 원래 기록을 보존한다. 동일 내용의 형제도 실제 node identity의 원문 순서로 정렬하며, 불완전 parse에서는 제목 범위를 확정하지 않는다. 선택 내용·인용 후보·SourceAnswer 계약은 유지한다. 구조 표현량까지 기존 source_context_tokens 예산에 포함하며 초과 시 실패를 기록한다. `source_format="flat"`으로 이전 평면 입력을 재현한다. 제품은 평가 디렉터리·질문 ID·정답을 참조하지 않는다.

저장 8개 입력을 제품 query→json_call→ModelClient 경계로 통과시켜 기존 동결 요청의 메시지·스키마·설정 일치와 인용 복원을 확인했다. 실제 generate만 모의 처리했으며 추가 native0이다. 평면 재현 1개 입력도 제품 전송이 과거 기준선과 정확 일치했다. 실제 사용량은 첫4 input35086/output1084/모델256.328575초, 정상4 input30600/output337/모델185.664836초, 합 input65686/output1421/모델441.993411초다. 과거 8개 대응은 input59462/output1675/모델421.480803초다. 실제 provider 토큰과 UTF8/2 sourcecap 추정량은 다른 값이다. 실행 순서·모델 로드·캐시가 같다는 검증이 없으므로 시간 절감이나 일반 정확성을 주장하지 않는다.

관련 확장 검사 75통과·7실패였다. 7개는 원래 HEAD의 business_use를 메모리에 불러도 동일하게 실패한 기존 검수 fixture/계약 경계이며 이번 변경에서 수정하지 않았다. 원문 순서·버전 분리·미확인 주소·불완전 parse의 새 검사 5개는 통과했다. 의미 판정과 전송/형식 계약 통과는 별도 증거다.
