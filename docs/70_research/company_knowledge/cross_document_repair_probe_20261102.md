# 다른 마트 문서에서의 선정·검수·보강 전이 검증

> 이 문서는 수정 전 실험의 기록이다. 같은 실패 사례를 수정한 뒤의 결과는 [사실 소속·인용 위치 수정과 보강·재검수](cross_document_repair_fixes_20261102.md)에 별도로 기록했다. 아래 실패·미실행 결과는 변경하지 않았다.

**새 문서의 실제 누락을 보강·재검수까지 해결한 사례는 이번에 없었다.** 두부조림에서는 이미 저장된 세 정보를 정상으로 판단하고 보강 없이 종료했다. 고춧가루 상품은 사실 연결 오류로 선정에서 중단했고, 돼지고기 부위 안내는 누락 두 가지를 지적했으나 근거 위치가 틀려 보강으로 넘기지 못했다. 이전 김치찌개 수량 두 건의 완료 성과를 다른 문서의 전체 흐름 성공으로 확대할 수 없다.

## 진행 이유와 고정한 기준

이전 [수량 두 건 보강](initial_build_quantity_repair_20261102.md)이 노출된 한 질문에만 맞춘 개선인지 확인하기 위해, 기존 공개 마트 자료에서 다른 문서 세 개와 새 질문 세 개를 골랐다. 상품 표시 정보, 긴 설명문, 재료·조리 목록을 포함했다. 정상 지식을 불필요하게 보강하는지도 별도 사례로 검사했다.

- 제품 코드·프롬프트는 `a27dfc0179c76ff4be5a976f9a757416f961121f`로 고정했다. 이번 세 문서용 정답·예시·지시를 추가하지 않았다. 새 제품 코드 변경은 없다.
- 원본 DB는 `retail_enabled_execution_20261024/service/knowledge.db`, 최초 추출 run은 `3aca51497d4142f9b428ebf16160feb9`, 추출 완료 run은 `54582ed647c440e89b327caba966b185`다. 두 run의 197개 자동 구축 지식이 동일하며 기존 보강·검토자 편집이 없다. 문서별 원시 추출 응답과 현재 기준선의 대응도 확인했다.
- 각 문서는 별도 복사 DB·새 run에서 검사했다. 원문이나 지식을 지워 누락을 만들지 않았다. 승인 44개 버전·통제 시연 v2·다른 DB의 승인 결과와 합치지 않았다.
- 모델 호출 전에 질문, 예상 누락 네 항목과 정상 다섯 항목, 중단 기준을 저장했다. 실제 누락을 알고 고른 목적 표본이며 무작위·맹검 평가가 아니다. 구문 두 개가 한 문장에 있는 부위 안내의 보관 정보는 두 검사 항목으로 구분했다. 이 9개를 전체 그래프 정확도·정밀도·재현율의 분모로 쓰지 않는다.
- 값 선정→사용 목적 선정→원문·저장 대조→업무 최종 검수→필요한 보강→자체 검수·재검수 순서로 진행하도록 준비했다. 실패하면 종속 단계를 중단하고 독립 문서만 계속했다. 같은 구성 재시도, 원시 응답 편집, 인용 검사 완화는 없다. 단계 진행과 의미 평가는 세션이 감독했다.

### 고춧가루: 올바른 값을 찾은 뒤 연결을 잘못 생성

질문은 “참맛고춧가루의 보관 장소와 개봉 후 보관 방법은 무엇인가요? 원재료는 무엇인가요?”다. 원문에는 다음이 있으나 처음 두 가지는 저장 표현에 없다.

- 직사광선을 피해 그늘지고 서늘한 곳에 보관하십시오.
- 개봉후 지퍼로 밀봉하여 냉장보관 하시면 고춧가루 특유의 맛을 오랫동안 유지할 수 있습니다.
- 건고추100%(국산): 기존 `claim_8e965dcdb0003aa5eb008ce4`의 원재료 값.

값 선정은 보관 장소→보관 문장, 개봉 후 방법→밀봉·냉장 문장, 원재료→건고추를 각각 올바르게 연결했다. 개봉 조건과 맛을 유지할 수 있다는 조건부 표현도 보존했다.

다음 선정은 이 세 사실을 각각 올바른 항목에 사용하면서, 제품을 식별한다는 이유로 **상품명·식품 유형·내용량 항목에도 같은 사실 ID 세 개를 다시 붙였다.** 프로그램이 이미 아는 소속과 다르므로 `selected_fact_owner_mismatch` 세 건이 발생했고 두 요청의 해당 항목이 미확정이 됐다. 원문 대조는 실행하지 않았다. 이것은 “정상 원재료를 검수가 정상으로 판정했다”는 성과가 아니다.

### 부위 안내: 누락 판단은 맞았지만 원문 위치가 틀림

질문은 “돼지고기 부위 안내에서 지방이 많은 부위의 냉장 보관 시 소비 권고와 장기 보관 방법은 무엇인가요? 앞다리에 알맞은 요리는 무엇인가요?”다.

원문은 “지방이 많은 부위는 냉장 보관 시 가급적 빨리 소비하고, 장기 보관할 때는 소분해 냉동하는 것이 좋다.”라고 되어 있다. 두 권고는 최초 저장 표현에 없다. 정상인 앞다리→국물 요리는 `claim_7686c7606f3419d5fa29c17c`에 있다.

모델은 원문·저장 대조에서 두 보관 권고를 missing, 앞다리의 국물 요리 용도를 represented로 반환했다. 정상 기여는 실제 `raw.Head`, `raw.Relation`, `raw.Tail`에 정확히 연결했다. 그러나 누락 근거 위치는 아래처럼 틀렸다. 인용 문구 자체는 원문에 정확히 한 번 존재한다.

| 누락 인용 | 모델이 반환한 절대 범위 | 실제 범위 |
| --- | --- | --- |
| 지방이 많은 부위는 냉장 보관 시 가급적 빨리 소비하고 | `[638,672)` | `[647,677)` |
| 장기 보관할 때는 소분해 냉동하는 것이 좋다 | `[673,695)` | `[679,703)` |

제품은 `missing_reference_unverified`와 `remainder_without_source_address`를 남기고 누락 근거를 채택하지 않았다. 실제 위치는 진단 파일에만 기록했다. 원시 응답의 숫자를 수정하거나 인용을 자동 재배치해 통과시키지 않았다. 따라서 **모델의 두 누락 인식은 확인했지만, 제품이 보강에 사용할 수 있는 누락 두 건을 확보한 것은 아니다.** 보강·재검수는 미실행이다.

이 문서에서는 다른 약점도 관찰했다. 원문 사실 여섯 개가 같은 본문 전체를 인용했고, 프로그램이 세 검사 범위를 각 사실에 연결하면서 18개 사실 기록을 만들었다. 다음 요청에는 1,267자 본문이 39번 반복됐다. 모델은 필요한 보관 사실을 골랐지만 입력 비용이 커졌다. 앞다리 국물 요리를 `necessary_premise`로 표기한 점도 남긴다. 직접 답하는 성격이 있으나 대상·속성·필수 여부는 보존됐다. 모델이 추가로 고른 ‘앞다리 유자 완자’는 같은 질문의 요리 예시로 원문에 있으나, 미리 정한 성공 항목 수에 추가하지 않았다.

### 두부조림: 이미 있는 수량을 다시 보강하지 않음

질문은 “두부조림 4인분의 두부 수량과 간장 수량은 각각 얼마인가요? 두부를 써는 크기는 어떻게 되나요?”다.

원문 대조는 두부 250g, 간장 30g, 써는 크기를 각각 아래 후보의 `interpretation.meanings.0.conditions.text`에 연결했다.

- 두부: `claim_76f22de1d85d5e1a61c64dae`
- 간장: `claim_132d5181a212a571a2347a01`
- 써는 크기: `claim_e97985d4a2407d1fcfef1d60`

재료명만 보고 수량이 빠졌다고 하지 않았다. 실제 저장 해석의 대상·재료·4인분 범위도 대조했다. 업무 최종 검수는 두 요청을 모두 범위 내 충분으로 판단했고, “4인분 기준 두부 250g, 간장 30g”과 “3cm×5cm×1cm로 썬다”를 유지했다. 실제 보강 함수도 호출했으며 생성 없이 `no_verified_gap`, 추가 0건으로 끝났다.

이 세 정상 정보에 대한 오탐·불필요한 보강은 관찰되지 않았다. 원래 저장 해석의 다른 유형·양태 필드까지 정상이라고 인증한 결과는 아니다. 변경이 없으므로 추가 후보 검수와 보강 후 재검수를 호출하지 않았고, 이를 재검수 성공 횟수로 계산하지 않는다.

## 프로그램·저장·실행 비용

- 세 복사 DB 모두 원본 모든 행·197개 지식·원래 그래프·528개 개념·원문을 보존했다. 각 DB에는 새 run·요구·요구 개정 행만 하나씩 추가됐다. 원본 DB SHA256은 불변이다. 새 지식·승인·사용 버전 전환은 모두 0이다.
- 세 DB 각각 실제 제품 FastAPI 라우터의 격리 포트에서 run GET HTTP 200과 저장값 일치를 확인했다. 모델 원시 응답 16개가 전송 요청·제품 저장 결과와 일치한다. 실패·미확정 기록도 조회된다. 자체 임시 서버만 닫았고 기존 서버를 재시작하지 않았다. 이번 UI 검증은 수행하지 않았다.
- 제품 코드가 바뀌지 않았으므로 이전 관련 검사 272개를 새로 실행한 것처럼 보고하지 않는다. 이번 무모델 검증은 코드·입력 동결, 최초 native 추출 대응, 저장 필드 대조, 원본 보존, 원시 응답 동일성, 실제 서비스 GET, 정상 사례의 보강 호출 0건을 확인했다.
- 새 로컬 Q4 **16회**: 고춧가루 4회, 부위 안내 6회, 두부조림 6회. 입력 **161,600**, 출력 **18,728**토큰, 호출 시간 합계 **2,036.778초**. 분석·준비·저장 확인 시간은 제외한다. 상한 29회 중 미사용 13회는 폐기했고 남은 호출은 0이다. 이전 수량 사례 계보 18회와 10월의 닫힌 6회 계보는 별도로 보존한다.
- 기존 26개 고유 원문 검수 응답을 확인했으나 현재 단일 문서 입력과 배치 범위·요청이 정확히 일치하지 않아 새 생성으로 재사용하지 않았다. 원래 구축 결과·파싱·벡터를 재구축한 것은 아니다. 이번 16회 중 원문 사실 구성은 4회다.
- 설치된 `qwen3.8:27b-q4_K_M`, temperature 0, think false를 역할별로 순차 실행했다. context는 실제 요청에 따라 16,384/24,576/32,768/57,344, 출력 예약은 4,096 또는 8,192다. 모든 호출은 정상 stop, 제공자 실패·잘림·동일 구성 재시도는 0이다. 관측 최대 pressure 값은 2, 동시 모델 최대 1, 메모리 기준 중단 0이다. 의미·참조 실패를 자원 실패로 바꾸어 보고하지 않는다.
- 부위 안내의 두 번째 선정은 준비 도구의 49,152 상한에서 호출 전에 한 번 거절됐다. 측정 입력 41,484 + 출력 8,192 + 스키마 별도 여유 755 + 안전 여유 1,000 = 51,431이므로 **그 단계만** 57,344로 준비했다. 프롬프트·스키마·제품 입력이 이전 준비본과 동일함을 확인했다. 이 과정은 모델 재시도가 아니며 최초 거절과 용량 변경 기록을 모두 보존했다.

## 이전 두 수량에만 맞춘 개선인가

새 두부·간장 수량과 보관 속성을 찾고, 수량이 이미 있는 사례에서 보강하지 않은 부분 성과는 있다. 해당 생산 코드에 이전 음식명이나 200g·120g 정답을 넣은 방식도 아니다. 그러나 **실제 누락이 있는 추가 문서 두 개에서 보강·재검수 완주는 0개**다. 다른 문서에서도 전체 흐름이 안정적으로 작동한다거나 일반화가 완료됐다고 결론 내릴 수 없다. 이전 코드와 새 코드의 독립 A/B 효과량을 측정한 실험도 아니다.

관찰된 다음 작업은 구체적이다.

1. 고춧가루처럼 모델이 올바른 보관 사실을 고른 뒤 상품 기본 정보 아래에 다시 붙이지 않도록, 이미 알고 있는 사실 ID→원문 사실의 소속을 프로그램이 전달하고 모델이 같은 소속을 다시 생성하는 부분을 줄이는 경계를 검토한다.
2. 부위 안내처럼 인용 문장은 맞고 숫자 위치만 틀리는 문제는 원문 구절 선택과 위치 확정을 분리하는 방식으로 검증한다. 정확히 일치하는 실제 위치만 허용하고, 여러 위치·범위 밖·원문 변경은 별도로 검사해야 한다. 이번 실패 응답을 사후 수정한 것으로 성공 처리하지 않는다.
3. 긴 본문을 사실 수만큼 반복 전달하는 부분은 동일 참조를 재사용하도록 줄일 필요가 있다. 입력을 줄였다는 사실과 의미 정확도가 유지된다는 증거는 따로 확인한다.

이번에는 세 사례를 보고 코드를 조정한 뒤 같은 사례를 다시 통과시키지 않았다. 위 변경은 별도 후속 검증 범위다. 새 제품 반영의 일반 성공 근거는 확보하지 못했으며, 결과 문서만 Draft PR #679에 추가한다. 기본 UI 자동 진행과 이전 승인 답변의 판단 한계 문장 인용 문제도 별도 미완료로 유지한다. 현재 사용자 결정이 필요한 사항 없음. 사용 버전 승인·전환, PR 병합·배포는 하지 않았다.
