# 검수 주장 근거 합집합의 선택적 사용과 동일 엔진 확인

2026-10-19. 같은 M02 질문 한 쌍에서 전체 입력 구성과 인용 가능 범위의 제한된 효과를 확인했다. `evidence_union`을 명시한 요청에만 사용하며 기본 요청 동작·모델·한도는 바꾸지 않는다. 전체 마트 목표나 다른 질문의 성능 검증을 완료한 것은 아니다.

## 변경 경계

- 기본값 `evidence_union=None`은 기존 선택과 반환을 유지한다.
- `evidence_union="selected_factual_claims_v1"`은 `snapshot_id`, `hipporag2`, `synthesis`, 빈 `requirement_ids` 조합에서만 허용한다. `limit`는 **기준 검색 선택 수**이며, 명시적 실험 계약 아래 전체 합집합 반환 수는 이를 넘을 수 있다.
- 기준 주장·원문·조건·검수 상태를 모두 보존한다. 실제 선택 edge가 같은 snapshot의 accepted factual claim에 정확히 연결되고 기존 ranked passages에 있으며 기준 집합에는 없을 때만 추가한다. `has_concept`는 제외한다.
- 추가 집합 전체를 기존 원문 순위와 passage 내부 순서대로 붙인다. 동일 claim ID만 중복 제거하고 같은 block의 다른 주장이나 출처·Scope가 다른 주장은 의미 병합하지 않는다. 선택 모델의 판단을 새 사실 승인으로 취급하지 않는다.
- 공용 `graph_retrieval.retrieve`가 합집합을 구성하고 `claim_union`에 기준·추가 ID와 반환 수를 남긴다. `execution_boundary.evidence_union`에 opt-in과 `limit`의 의미를 기록한다. 후보·관계 선택·PPR·QA 지시·원문 문맥·입력 투영은 변경하지 않았다.
- 전체 QA 입력이 기존 guard를 넘으면 **QA 전송을 중단**한다. 기준 근거 삭제, 추가 근거 일부 선택, 자동 압축이나 한도 증가는 하지 않는다. context 49,152·출력 예약 8,192·안전여유 1,000을 유지한다.

## 원문 신규성 평가의 정정

처음에는 새 `source_evidence` 재료 구간을 QA에 처음 전달된 원문 사실로 판단했다. 전체 wire를 대조하니 기존 `reviewed_meanings`에 이미 전체 재료 인용이 있었다. 새 고유 원문 정보는 **0개**이며 추가된 직접 주장·검수 의미·인용 연결은 **4개**다. 원래 단계의 passed 기록과 정정 후 사전 min1 미충족을 함께 보존하며, 그 gate를 사후 통과로 바꾸지 않는다. 기존 답변의 누락을 원문 정보 미전달만으로 설명한 가설도 철회한다.

사용자의 별도 승인으로, 기존 union 응답을 재생성하지 않고 같은 엔진의 누락 기준선 QA만 1회 추가했다. 이는 같은 구성의 대조 단계이며 새로운 변형이나 실패 계보 초기화가 아니다. 직접 연결·인용 가능성·동일 인용 반복 중 어느 부분이 답변 차이를 만들었는지는 분리하지 못했다.

## 같은 엔진 한 쌍의 결과

두 실행은 Ollama 0.40.6, `qwen3.8:27b-q4_K_M`, Q4_K_M과 같은 model digest를 사용했다. 실제 native 옵션은 temperature 0·num_ctx 49,152·num_predict 8,192·think false·stream false로 동일하다. 기준선은 저장된 원래 messages와 schema를 그대로 사용했다. schema 차이는 제공 주장 수에 따른 citations enum과 maxItems 12→16이다. 따라서 메시지 내용만의 순수 효과로 해석하지 않는다.

| 항목 | 기존 입력 기준선 | 합집합 입력 |
| --- | --- | --- |
| 제공 주장 / 원문보기 / 검수 의미 | 12 / 17 / 12 | 16 / 21 / 16 |
| 원문보기의 고유 block 수 | 17 | 17 |
| 요청된 공통 재료의 실제 답변 | 1종 | 5종 |
| 기존 온도·개봉 후 보관 조건과 두 상품 식별 | 유지 | 유지 |
| 제조원·태안 보관의 자료 공백 | 확인 불가 | 확인 불가 |
| 김치찌개 조건부 OR의 답변 명시 설명 | 없음 | 없음 |
| 제공 ID에 연결된 실제 인용 | 5개·4출처 | 9개·4출처 |

공통 재료 나열만으로 양쪽 모두 항상 의무라는 오류를 추정하지 않았다. 조건이 입력에 남는 것과 답변이 이를 실제 설명한 것은 구분한다. 응답 자체는 전역 인용 배열이며 문장별 인용 대응은 저장 원문 감사로 작성했다. 형식상 `answered`와 전체 질문 충족도 별개다.

기준선에는 전체 재료 인용이 있었지만 답변은 이를 미제공으로 설명했다. 합집합은 기존 정상 조건의 중대한 회귀 없이 요청된 재료를 더 활용했다. 이 한 쌍은 **전체 입력 구성과 인용 가능 범위의 제한된 효과**를 지지한다. 새로운 원문 정보 획득·일반 성능·세부 작동 원인이나 전면 기본 채택을 입증하지 않는다.

## 검증과 비용

동결 제품 3파일·검사 1파일의 해시가 동일하여 102개 고유 검사 통과(합집합 관련 10개 포함)와 동일 10개의 마지막 재확인을 재사용했다. 이를 112개로 합산하지 않는다. 기본 경로, 동일 ID만의 중복 제거, 유효 factual 연결, 전체 추가 집합, 범위 밖 요청 거절, 용량 초과 시 모델 전송 차단을 검사했다. 추가 전체 검사나 모델 반복은 하지 않았다.

| 실제 provider 관측 | 기준선 | 재사용한 union |
| --- | ---: | ---: |
| 입력 토큰 | 20,084 | 25,255 |
| 출력 토큰 | 329 | 363 |
| client 요청 시간(초) | 140.236253 | 177.846382 |

차이는 입력 +5,171·출력 +34토큰, client +37.610129초다. 두 실행 모두 전송 직전 상주 모델이 없었고 provider load는 각각 약 5.852·5.860초였지만 OS/파일 캐시와 비트 단위 연산 동일성은 통제하지 않았다. 단일 쌍의 시간을 일반 속도 성능으로 해석하지 않는다. 공용 guard의 보수 추정 40,303·48,331은 실제 provider prompt 토큰과 구분한다.

이번 추가 확인은 기준선 QA 1회·union 재생성 0회·검색/PPR/관계 선택/임베딩 0회·모델 재시도 0회다. 전송 전 격리 DB 등록 오류는 native 0회인 준비 실패로 별도 보존했다. 원본 DB·raw·원응답·평가 기준·실행 전용 스크립트는 이 변경에 포함하지 않는다.

## 제한 채택과 잔여

현재는 명시적 옵션 범위로만 제한 채택한다. 기본 요청, 모델, 한도는 그대로다. 양쪽 전체 M02는 부분충족이며 제조원·태안 관계 선택/보관 공백과 M03 용도는 별도 미완료다. PR 병합·배포·이슈 종료는 하지 않는다.

기존 기록과 정정은 보존한다. 계보는 narrow≥9 / broad≥10, global·remaining unknown, 닫힌 semantic 6/6, no_reset을 유지한다. 이전 입력 예산 단계는 [모델 입력 예산 후속 기록](retail_model_input_budget_20261019.md)과 구분한다.
