## 현재 경계와 다음 검증

새 조건의 관련성 판정과 같은 block 내부 독립성은 서로 다른 남은 항목이다. 전자는 기존 연결 없는 요구의 범위·조건과 실제 변경을 비교해야 하고, 후자는 같은 block 안의 의미·필드·전제별 원문 주소와 의존을 확인해야 한다. 기존 버스13/12는 이 둘의 대체 증거가 아니다. 아직 새 실제 자료·실행을 선정하지 않았으며 위 표는 완료 기준 대응표다. 모델 실행 전 자료의 기존 노출·시도 회차와 원인 변경을 조정 세션에서 확인해야 한다.

다음 작은 대조의 입력·출력은 아래와 같다. 실제 자료가 선정·동결되기 전에는 실행하지 않는다.

| 대조 | 필요한 입력·선행조건 | 확인할 출력 |
|---|---|---|
| 새 조건 관련 요구 1개 + 비영향 대조 1개 | 실제 전후 원문과 diff, 두 요구의 범위·조건·현재 평가·원문 주소. 관련 요구에 기존 경로가 없음을 확인하고 사례의 역사적 회차를 동결한다. 별도 DB/run 사용 | 변경 ID·이유를 가진 실제 `affected/new_relevance`와 대조 `unaffected`; 변경 이력·needs_review 저장 및 재조회. mock 결과와 실제 판정을 분리한다 |
| 같은 변경 block의 변경 의미 1개 + 정상 의미 1개 | 실제 같은 block의 전후 주소, 두 의미·조건·전제·후보/필드 근거와 현재 평가. 정상 의미의 내용 유지와 변경 부분에 의존하지 않는 근거가 필요하다. 현재 block 전체 제외를 줄이려면 해당 증거와 최소 조회 경계안을 먼저 검토한다 | 변경 의미의 옛 근거는 제한되고, 독립성이 확인된 정상 의미만 저장·조회에서 보존되는지 확인한다. 의존·주소가 불명확하면 미확정으로 남긴다. 단순 `unaffected` 한 행으로 모든 옛 후보를 재허용하지 않는다 |

UI는 이미 연결된 `3014/8014`의 동일 계약으로 검증한 기록만 재사용한다. 보존 중인 구 `8012`에는 당시 `/workbench/usage`가 없어 HTTP404였으며 서로 다른 서버 계약을 섞으면 검증이 성립하지 않는다. `explicit_query_only`는 일반 활성화나 사람 승인 상태가 아니다. 현재 코드·정적 계약과 해당 실제 자료에 맞는 제품 통합이 선행되어야 새 화면 검증을 추가할 수 있다.
