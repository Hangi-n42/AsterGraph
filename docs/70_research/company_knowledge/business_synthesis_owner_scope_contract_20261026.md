# 종합 출력 대상 ID의 허용 범위 고정 — 2026-10-26

## 진행 이유와 범위

기준은 원격과 같은 `21eb9b0bc46452ed14f59706ed124331947d5e6c`다.
별도 `codex/synthesis-owner-scope` 브랜치에서 #616의 종합 출력 계약만 보강했다.
원본 G 실행의 원시 응답은 참고용 의존성 10행을 그대로 반환했고,
서버는 수정 허용 5개 키 밖의 행 5개를 거부했다. 기존 판정·원시 실패는 그대로 보존한다.

입력의 참고 범위와 출력의 갱신 범위는 다르다.
현재 사례는 source/local 판정 10개, 종합에서 갱신할 수 있는 대상 5개다.
응답 `checks`와 `dependencies`는 모두 이 5개 대상만 허용한다.
`source_checks` 10개는 서버가 보존하며 종합 응답 필드가 아니다.
공개 항목의 참고 의미와 의존성의 전제 참조는 갱신 대상 밖의 알려진 의미도 사용할 수 있다.
따라서 참고 문맥을 5개로 삭제하거나 갱신 권한을 10개로 늘리지 않았다.

## 최소 변경

기존 `split_roles` 종합의 최종 동적 Pydantic 타입을 상속한다.
`checks`/`dependencies` 각 행의 `meaning_key`만 실제 `join_keys`의 Literal로 제한했다.
기존 행 타입을 상속하고 목록 FieldInfo를 복사해 필수 잔여 필드·최소 행 수·보존/공개 항목 제약을 유지했다.
활성 지시에도 허용 대상 ID만 반환하고, 같은 값이라도 범위 밖 재출력은 금지하며 생략은 기존 판정 보존임을 명시했다.

공통 `MeaningDependency` 모델, 원문·local 입력, 공개 항목의 전체 의미 enum과 전제 끝점 타입은 변경하지 않았다.
알려진 전체 의미를 향한 교차 범위 전제는 유지하고, 모르는 끝점·중복·근거 오류는 기존 consumer가 거부한다.
빈 범위의 기존 maxItems=0 처리와 모든 소비 검증도 유지한다.
범위 밖 응답을 사후 삭제하거나 검증을 완화하지 않았다. 새 의존성·설정·범용 스키마 도구는 없다.

## 송신 형식과 조기 실패의 실제 서비스 경계

실제 `json_request → selected_evidence_type → ModelRequest → Ollama format` 경로를
HTTP MockTransport로 실행했다. 송신 format 스키마와 메시지가 캡처한 새 요청과 같았다.
모의 HTTP 요청은 2개이고 실제 모델·토큰 계수 서버 호출은 0이다.
원시 응답 보존 및 상태 전파를 메모리에서 확인했으며 원본 DB를 쓰지 않았다.

- 원시 G와 같은 혼합 응답은 JSON 파싱 후 일단 succeeded가 됐지만,
  대상 5개의 스키마 위반으로 최종 unit이 `failed/schema_error`, `json_call`은 None이 됐다.
  consumer는 `synthesis_call_failed`로 처리하고 기존 compact의 checks/dependencies/source_checks를 보존했다.
  잘못된 5행만 잘라 통과시키지 않는다. 원시 parsed 10행과 오류도 그대로 남긴다.
- 별도 허용 5행 fixture는 unit succeeded와 consumer joined를 통과했다.
  fixture의 satisfied=false는 유지했다. 이것은 전체 요구 충족이나 새 모델의 출력 성공이 아니다.
- 두 경우 모두 메모리 fixture의 199개 주장·그래프·개념·교정 receipt·기존 assessment가 같았고,
  새 보강 2개의 represented 위치도 보존됐다.

조기 거부는 혼합 응답의 새 갱신 전체를 적용하지 않는 동작이다.
일부 유효한 변경 행이 함께 있어도 이전 판정을 보존하며, 이를 부분 성공으로 재표기하지 않는다.
실제 모델에서 같은 결과가 나는지와 출력 제약 준수율은 미검증이다.
