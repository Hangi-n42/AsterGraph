# 최초 구축본 수량 두 건: 선정부터 보강·재검수까지

**배추김치→수량 200g, 돼지고기→수량 120g을 실제 모델 출력에서 각각 연결했고, 최초 자동 구축본의 같은 누락 두 건을 검수가 발견한 뒤 보강·재검수까지 통과했다.** 노출된 레시피 한 문서·질문 한 개에 대한 제한 검증이다. 전체 그래프 정확도나 무감독 자동 교정의 일반 성능으로 확대하지 않는다.

## 왜 이 범위로 확인했는가

직전 [실패 기록](initial_build_repair_probe_20261102.md)은 수량 두 개를 각각 묻는 질문을 집합 비교로 출력해 후속 검수를 실행하지 못했다. 이번에는 같은 최초 구축본·같은 원문·같은 두 누락을 유지했다. 누락을 만들기 위해 지식을 삭제하거나 정답을 제품 입력에 주입하지 않았다.

기준은 원본 `retail_enabled_execution_20261024/service/knowledge.db`의 최초 추출 run `3aca51497d4142f9b428ebf16160feb9`와 추출 완료 run `54582ed647c440e89b327caba966b185`다. 두 run의 197개 지식은 동일하고 기존 교정·검토자 편집은 없다. 해당 레시피 전체 10개 저장 표현과 전체 197개 저장 표현을 조사했다. 원문 인용에 남은 숫자는 저장된 수량 명제로 계산하지 않았다.

원문 버전은 `f1ed24e0d5d24e4988c556d134574269`, 재료 block은 `51ec34b423e647808e89a8f8dba4a4b7`이다. 승인 44개 버전이나 통제 v2를 이 기준선과 합치지 않았다. 수량을 직접 묻는 아래 질문을 사용했으며 기존 M03의 필수 요구를 바꾸지 않았다.

> 김치찌개 레시피의 배추김치 수량과 돼지고기 수량은 각각 얼마인가요? 돼지고기의 부위는 무엇인가요? 간을 추가하는 조건과 사용할 재료는 무엇인가요?

## 무엇을 바꿨는가

1. **검사 방식과 실제 대상을 출력 필드로 명시했다.** 모델이 단일 대상 확인·집합 내부 비교·서로 다른 대상 비교 중 하나를 먼저 선택하고 대상 구절과 공통 속성 하나를 연결한다. 실제 출력은 `김치찌개 레시피의 배추김치→수량`, `돼지고기→수량`이라는 별도 단일 대상 검사였다. 중복 문구의 위치는 기존 프로그램이 처리한다. 내부 디코딩이 이전 실패의 원인이었다는 인과 주장은 하지 않는다.
2. **대상·속성별로 실제 값을 고르게 했다.** 모든 원문 묶음마다 무엇인가를 채우게 하지 않고, 이미 정한 검사 범위에 해당하는 값을 선택한다. 목록 파서가 알고 있는 재료명–수량 짝은 재사용한다. `200g`은 배추김치, `120g`은 돼지고기(등심)에 연결되며 식품 분류나 제목을 수량으로 선택하지 않았다. 선택 가능한 동일 사실의 문맥 주소와 조건 상태의 의미도 입력에 명시했다. 기존 주소·소유권 검사는 완화하지 않았다.
3. **검수의 실제 누락을 보강 함수에 연결했다.** 원문 검수의 missing/partial과 업무 검수의 필수 부족이 같은 대상을 가리킬 때만 추가 후보를 생성한다. 기존 지식은 수정·삭제하지 않는다. 정확한 원문·버전·누락 범위와 참여자 근거를 검사하고, 추가 후보 자체의 원문 검수 및 새 원문·업무 재검수를 모두 요구한다.
4. **빠진 대상 근거 선택을 문장 생성과 분리했다.** 보강 모델은 올바른 수량 문장을 만들고도 `김치찌개`의 근거 줄을 두 번 빠뜨렸다. 첫 지시 보완도 실패했으므로 같은 계열의 지시 조정을 중단했다. 기존 원시 제안·문장·Entity·조건·기간을 고정하고, 빠진 이름의 실제 원문 위치 중 하나만 별도 모델이 선택하게 했다. 두 문장 모두 `음식명: 김치찌개`를 선택했다. 별도 파생 후보와 근거 선택 기록을 만들었으며 원시 응답을 사후 편집하지 않았다.

새 경로는 기존 `request_reference_review`의 명시적 실험 단계다. `business_selected_repair.py`가 누락 연결·추가·재검수 완료를, `business_selected_repair_evidence.py`가 추가 근거 선택을 담당한다. 이전 질문·사실 선정·업무 검수 계약은 버전별 재생 검증을 위해 유지한다. 기존 승인 44개 답변 연결도 이전 계약으로 재검증했으며 새 모델 효과로 세지 않는다.

## 프로그램·보존·비용 확인

- 관련 프로그램 검사 **272개 통과, 19.38초**. 합성 검사는 입력 변경, 대상·버전 불일치, 미확정, 근거 이탈, 중복, 실패 시 원본 보존, 새 자체 검수·재검수 요구를 확인한다. 모델 의미 정확도의 점수가 아니다.
- 원본 DB SHA256 불변. 원본 모든 행과 197개 지식, 기존 그래프 구성, 당시 개념 기록 528개를 보존했다. 528은 이 최초 구축본의 기록이며 이후 530개 연결 성과와 다른 기준이다. v8 부모 DB의 모든 행·상속 모델 응답·실패 보강 기록 두 개도 그대로 보존했다.
- 실제 제품 FastAPI 라우터의 격리 포트에서 run GET HTTP 200, 저장값과 응답 일치를 확인했다. 자체 임시 서버만 닫았다. UI 시연은 수행하지 않았다.
- 완료 후 동일 보강 요청은 `no_verified_gap`, 새 모델 호출·추가 지식 0건이었다. 오래된 누락 판정으로 재보강하려는 요청도 차단했다.
- 이번 요청 **로컬 Q4 16회**, 입력 153,197 / 출력 12,058토큰, 호출 시간 합계 1,542.585초. 직전 v1·v2까지 합친 이 사례 계보는 **18회**, 입력 157,863 / 출력 13,763토큰, 1,659.260초다. 준비·테스트·분석 시간은 호출 시간에서 제외했다. 이전 10월의 닫힌 6회 계보는 별도 보존하며 초기화하지 않는다.
- 설치된 `qwen3.8:27b-q4_K_M`, temperature 0, think false. 실제 요청별 context 16,384/24,576/32,768, 출력 예약 4,096 또는 8,192를 사용했다. 전송 직전 동일 입력·스키마·한도를 검사했고 모든 native 호출은 정상 종료했다. 실패 원인을 메모리·잘림·형식 실패로 바꾸어 보고하지 않는다. 동시 모델 실행·외부 모델·다운로드는 없다.

## 제품 반영 범위와 다음 작업

명시적 실험 경로의 코드와 제한 실증을 Draft PR #679에 포함한다. 기본 UI의 자동 진행이나 운영 사용 버전으로 전환하지 않는다. 단계 진행·중단과 의미 평가는 세션이 감독했으며, 주소 검사로 발견하지 못한 의미 오류를 제품의 자동 발견 성과로 계산하지 않는다.

현재 확인한 것은 노출된 한 질문에서의 실제 두 누락 보강이다. 다른 문서·질문의 선정 정확도, 정상 지식을 잘못 보강할 위험, 오류 문장 교체의 일반 성능은 미확인이다. 다음 검증은 이 두 수량을 정답으로 노출하지 않은 별도 사례에서 누락 탐지와 정상 보존을 함께 확인하는 것이다. 기본 UI 연결과 과거 답변의 판단 한계 문장 인용 문제도 별도 미완료로 유지한다. 이번 미승인 후보로 새 사용 버전이나 새 QA를 만들지 않았다.

현재 사용자 결정이 필요한 사항 없음. 새 승인·사용 버전 전환·PR 병합·배포는 하지 않았다.

후속 [다른 문서 세 개의 고정 코드 검증](cross_document_repair_probe_20261102.md)에서는 정상 두부조림의 불필요한 보강 방지는 확인했지만, 누락이 있는 두 문서의 보강·재검수 완주는 없었다. 위 한 질문의 성과와 실패 계보를 수정하거나 일반 성공으로 확대하지 않는다.
