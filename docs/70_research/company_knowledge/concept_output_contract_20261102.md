# 개념화 출력 계약 보완 — 2026-11-02

새 개념화의 생성 요청·소비·저장·재사용에 `json-array-v1`을 연결했다. 로컬 Gemma의 개체·사건·관계 3회 모두 정상 배열 생성과 실제 HTTP 저장·재조회가 확인됐다. 의미 정확도 향상은 확인하지 않았다. 기존 Gemma 응답도 이 세 사례에서는 적절했으며, 사건·관계의 개념 목록은 이전과 같다.

## 진행 이유와 변경

이전 제품은 개념화를 `schema=None`으로 요청하고 응답 전체를 쉼표로 나눴다. 따라서 `설명: 식품, 식재료`도 `설명: 식품`을 개념 이름으로 소비했다. 앞선 소형 모델 비교의 배열 실험은 제품 경로에 연결되지 않은 별도 실험이었다.

- 개체·사건·관계의 의미 지시와 원문·이웃·조건·주소는 유지하고, 고정 출력 예시와 출력 지시만 JSON 배열로 바꿨다. 원문을 넣기 전에 고정 예시를 변환하므로 사용자 자료를 재작성하지 않는다.
- 기존 `ModelClient`의 Ollama `format`에 문자열 배열 스키마를 전달한다. 새 모델·의존성·Outlines는 추가하지 않았다.
- 저장 전 **원시 응답 전체**를 파싱한다. 설명문/코드 블록에서 JSON을 찾아 구제하지 않는다. 잘린 응답, 객체, 문자열 하나, 빈 배열, 빈/공백 항목, 비문자열 항목은 개념으로 저장하지 않는다. 실패 원시 응답과 작업 기록은 보존한다.
- 원래의 공백 제거·소문자화·중복 제거는 배열 항목별로 유지한다. 항목 안의 쉼표를 새 개념 경계로 나누지 않는다.
- 준비 단계의 용량 계산, 실제 요청, 작업 지문, 재사용, 부분 재구축의 원형 연결, 완료 개념의 조회·저장 연결에 같은 스키마를 전달한다. 저장된 개념 이름과 실제 원시 응답의 소비 결과도 대조한다.
- 결과는 `unreviewed`, `has_concept`, `approved_is_a=false`이다. 배열 성공을 승인 유형 계층이나 의미 검증으로 바꾸지 않는다.

적용 경계:

| 경로 | 출력 계약 |
|---|---|
| 부모 없는 새 업무 지식 구축 | JSON 배열 |
| 선택한 대상의 새 개념화 실행 `/business/concepts` | JSON 배열 |

| 기존 결과 조회 | 재생성·승인 상태 변경 없음 |

과거 쉼표 응답을 새 배열 요청의 완료 결과로 재사용하지 않는다. 과거 계약을 유지한 요청은 당시 입력을 유지한다. 기존 5개 실제 개념화 입력의 메시지·선정 정보가 바뀌지 않는 것도 별도 대조했다.

## 실행·실패 계보

모델 실패와 검증 스크립트 실패를 구분해 보존했다. 생성 코드는 세 호출 내내 동일했다.

1. `retail_concept_json_contract_gemma_q4_20261102_v1`: 검증용 서버의 `/knowledge` 경로를 중복 결합하여 HTTP 404. 모델 0회. 무모델 검사와 수정 전 대조 로그도 이 폴더에 있다.
2. `..._v2`: 두부 생성 1회 성공. GET이 추가하는 파생 `counts`를 저장 본문과 직접 비교한 스크립트 오류로 중단. 원본 응답을 유지하고 두부 생성은 반복하지 않았다.
3. `..._v3`: 앞서 적재한 Gemma 때문에 호출 전 여유 메모리 기준을 통과하지 못한 기록을 보존했다. 자체 적재 모델만 해제하고, 동일한 메모리 기준·입력·스키마로 미실행 사건/관계 2회만 진행했다. 각 호출 후 자체 모델을 해제했다.
4. 최종 행 보존 검사에서 SQLite 정수 키 `knowledge_state:1`이 JSON 맵에서 문자열이 된 비교 오류를 발견했다. 별도 읽기 전용 `verify_result.py`가 원본·중간·최종 DB의 실제 키와 **행 전체**를 직접 대조했다. 모델 호출·응답 수정 없이 모든 기존 행 보존을 확인했다.

개별 중단 장부를 성공으로 덮어쓰지 않았다. 계보 전체의 최종 판정은 v3 `FINAL_STATUS.json`이다. 총 생성 상한 3회를 지켰고 더 실행할 예산은 남기지 않았다.
